## Issue: H2 p99 latency spike (~180ms)
Status: hypothesis (strong — multiple contributing factors identified)
Root cause:
  Three compounding allocation-related stall sources in the hot H2 request path:

  1. hpack_decode (h2_hpack.c:746) issues 2× strdup per header per request
     (~8 headers = 16 small mallocs per request). Under high concurrency these
     hit the allocator's central freelist when the thread-local cache is full,
     serialising all threads momentarily.

  2. dyntab_add (h2_hpack.c:580) doubles the ring buffer via realloc (line 597)
     when count == cap, then linearises it with a tmp malloc + memcpy (lines
     602-608). This is O(n) and happens at cap thresholds 16, 32, 64… —
     infrequent but unpredictable, matching p99 / rare-spike behaviour. Both
     hpack_rx and hpack_tx contexts can trigger this independently.

  3. hc->write_buf (h2.c) is grown with buf_append for every 9-byte frame
     header and payload in a single event-loop iteration. Under concurrent
     streams (max_concurrent_streams=200) write_buf can double several times
     in one pass of handle_events_worker, each realloc stalling the event loop
     thread (buf.c:26: realloc + memmove when off > cap/2).

  The perf "no hotspot >1%" result is expected: allocator latency shows up as
  kernel time spread across many frames, not as a single C function.

  routa_now_us() (2× clock_gettime per stream in dispatch_stream, lines 1055
  and 1081 of h2.c) adds vDSO overhead per-request but is unlikely to cause
  180ms spikes. Sampling every 16 frames (h2_conn_recv:1545) is fine.

Impact: high — degrades p99 SLA; invisible to median latency benchmarks
Fix:
  - Pre-size write_buf at h2_conn_new to estimated response size (avoid mid-
    stream realloc). Reserve at least 64KB at connection creation.
  - Pool hpack string allocations: use a per-connection arena bump allocator
    for hpack_decode output, freed in bulk at stream close.
  - Add per-stream latency histogram in debug builds: timestamp at
    h2_conn_recv entry, after hpack_decode, after dispatch_stream, after
    io_write_from_buf to pinpoint which step spikes.
  - Consider pre-allocating dyntab entries array to a fixed cap (e.g. 128)
    to eliminate the first few realloc/linearise calls.
Files: src/http/h2.c, src/http/h2_hpack.c, src/util/buf.c

## Issue: HTTP/1.1 + WebSocket broken pipe errors
Status: confirmed
Root cause:
  Two distinct sub-issues:

  1. The initial hypothesis ("event_loop_run doesn't set SIGPIPE SIG_IGN") is
     WRONG. Both server_run() (server.c:179) and event_loop_run()
     (event_loop.c:1601) call signal(SIGPIPE, SIG_IGN) before any I/O.
     Worker threads inherit the process-wide SIG_IGN disposition. Broken pipe
     errors during benchmarks are genuine EPIPE returns from write(), not
     signal-induced crashes. These are expected under high-concurrency when
     clients disconnect mid-transfer; they should be logged at DEBUG, not ERROR.

  2. ws_echo_server.c has a severe preprocessor bug: the #ifndef _GNU_SOURCE
     guard at line 2 has its matching #endif at line 74 (end of file), instead
     of immediately after the #define _GNU_SOURCE on line 3. When the build
     system passes -D_GNU_SOURCE (the standard Linux case), the entire file
     body — including main() — is conditionally excluded, producing an empty
     translation unit. Linking fails with "undefined reference to `main`" if
     this example is built with -D_GNU_SOURCE defined externally.

Impact: medium — broken pipe noise pollutes logs; ws_echo_server build broken
  under standard Linux build flags
Fix:
  - ws_echo_server.c: move the #endif to immediately after the #define line:
      #ifndef _GNU_SOURCE
      #define _GNU_SOURCE
      #endif          ← insert here, delete the one at line 74
  - Downgrade EPIPE log in io_write_from_buf / io_write_from_buf return paths
    from LOG_ERROR to LOG_DEBUG (client disconnect is normal under load).
  - Add a compile-test target for all examples to catch empty-TU issues.
Files: examples/ws_echo_server.c, src/net/io.c

## Issue: buf_t offset audit — lb_finish_forward direct .data access
Status: confirmed
Root cause:
  lb_finish_forward (lb.c:655) accesses resp_buf->data directly instead of
  using buf_data(resp_buf) at line 668:

      memcpy(raw, resp_buf->data, resp_buf->len);   ← BUG

  buf_data() returns data + off, accounting for bytes consumed via
  buf_consume(). If resp_buf->off is ever non-zero (because a caller called
  buf_consume before passing the buffer), this memcpy starts from the wrong
  offset, corrupting the response parsing.

  In the current event_loop.c call site (event_loop.c:518-524), upstream_resp_buf
  is never passed through buf_consume before lb_finish_forward — off is always 0.
  This makes the bug latent and safe today but fragile against any future
  refactor that adds buf_consume to the upstream reading path.

  Also in lb.c:643 (lb_begin_forward), the upstream_req_buf write path
  uses rb->data + conn->upstream_req_sent without going through buf_data(),
  which is safe only because buf_reset() (off=0) is always called first.

  A full audit of upstream.c found no additional raw .data accesses.

Impact: low (latent) — safe in current code; will silently corrupt proxy
  responses if upstream_resp_buf ever receives a buf_consume call
Fix:
  - lb.c:668: replace resp_buf->data with buf_data(resp_buf)
  - event_loop.c:982: replace rb->data + conn->upstream_req_sent with
    buf_data(rb) + conn->upstream_req_sent (and verify sent tracking logic
    relative to off)
  - Add a codebase-wide grep for '->data[^(_]' to catch future violations.
Files: src/lb/lb.c, src/core/event_loop.c

## Issue: rand() thread safety in lb.c (C-01)
Status: confirmed
Root cause:
  pick_p2c() (lb.c:173) calls rand() at lines 192 and 194.
  The LB_RANDOM branch in lb_pick_node() (lb.c:253) also calls rand().
  rand() uses global state in glibc and is not thread-safe — concurrent calls
  from multiple worker threads can race on the internal seed, producing
  non-uniform distributions or, on some platforms, undefined behaviour.
  srand() is called once in lb_new() (lb.c:508) seeding the global state.

  Under the epoll model each worker thread calls lb_pick_node concurrently;
  all workers share the same lb_t. For P2C, two rand() calls must select
  *distinct* candidates — thread interleaving can cause both calls to return
  the same value, defeating the load-balancing property.

Impact: medium — biased upstream selection under concurrent load; data race
  (UB in C11) on the global rand() seed; no memory safety impact
Fix:
  Replace rand() with one of:
  a) rand_r() with a per-worker seed (unsigned int stored in worker_t),
     passed down through lb_pick_node → pick_p2c/LB_RANDOM.
  b) An inline atomic xorshift32 seeded per-thread:
       static _Atomic uint32_t xseed = 0x9e3779b9u;
       uint32_t x = atomic_fetch_xor(...) — simple, fast, no locks.
  c) random_r() with per-connection state (heavier, not needed here).
  Option (a) is minimal change: add `unsigned int rng_seed` to worker_t,
  initialise to worker_id ^ time(NULL), pass to lb_pick_node.
Files: src/lb/lb.c, include/lb/lb.h (lb_pick_node signature), include/core/event_loop.h (worker_t)

## Issue: build_forward_request silently truncates large POST bodies
Status: confirmed
Root cause:
  build_forward_request (lb.c:291) is called with a 65536-byte stack buffer
  at two call sites:
    lb_forward      (lb.c:432):      char req_buf[65536];
    lb_begin_forward (lb.c:642):     char tmp[65536];

  The body copy at lb.c:317-321 is guarded by:
      if (req->body && req->body_len > 0 &&
          (size_t)n + req->body_len < bufsz) { ... }

  When the total headers + body exceeds 65536 bytes, the condition is false
  and the body is silently omitted from the forwarded request. The upstream
  receives a request with no body but with the original Content-Length header,
  causing it to hang waiting for data that never arrives (or return 400).

  This is not a stack overflow (65536 bytes << default 8MB pthread stack) but
  a correctness bug: large POST/PUT bodies are silently dropped with no error
  returned to the caller.

Impact: high — POST bodies >~64 KB are silently dropped in reverse-proxy mode;
  upstreams receive malformed requests; no error is surfaced to the client
Fix:
  Replace the fixed stack buffer with a heap allocation sized to the actual
  request:
    size_t need = <header estimate> + req->body_len + 512;
    char *buf = malloc(need);
    int len = build_forward_request(req, buf, need);
    ... (use buf) ...
    free(buf);
  build_forward_request should also return -1 if snprintf output was truncated
  (check n >= bufsz before each snprintf). For very large bodies consider a
  streaming / writev approach instead of buffering the entire request.
Files: src/lb/lb.c

## Issue: Chunked Transfer-Encoding from upstream not supported
Status: confirmed
Root cause:
  read_upstream_response (lb.c:326) and lb_finish_forward (lb.c:655) both
  only parse Content-Length to determine body length:
    read_upstream_response: lb.c:379 — `if (strcasecmp(line, "content-length") == 0)`
    lb_finish_forward:      lb.c:695 — `if (strcasecmp(line, "content-length") == 0)`

  When the upstream sends Transfer-Encoding: chunked (no Content-Length):
  - No body is read/copied into the response.
  - The raw chunked-encoded data in the receive buffer is discarded.
  - The client receives a 200 OK with an empty body.
  - No error is logged; the upstream connection is returned to the pool as
    healthy despite delivering an incomplete response.

  This violates HTTP/1.1 (RFC 9112 §7.1): chunked is the mandatory fallback
  when Content-Length is absent.

Impact: high — any upstream that uses chunked encoding (many modern HTTP
  frameworks do by default for dynamic content) silently returns empty bodies
  to clients; data loss with no error signal
Fix:
  Add chunked decoding in both read_upstream_response and lb_finish_forward:
  1. Detect Transfer-Encoding: chunked header during header parsing.
  2. Implement a chunked decoder: read hex size line, read chunk data,
     repeat until terminal zero-size chunk.
  3. Reassemble decoded chunks into resp->body via http_response_set_body.
  4. Alternatively, forward raw chunked bodies to the client without
     decoding (pass-through), which avoids buffering large bodies.
Files: src/lb/lb.c

## Issue: X-Forwarded-For and Via headers not added to proxied requests
Status: confirmed
Root cause:
  build_forward_request (lb.c:291) copies original request headers and rewrites
  Connection, but never injects:
    X-Forwarded-For: <client_ip>
    Via: 1.1 routa

  The client_ip is available: lb_forward receives it as a parameter (lb.c:409),
  and lb_begin_forward also receives client_ip (lb.c:586). However,
  build_forward_request does not take client_ip as a parameter (current
  signature: const http_request_t *req, char *buf, size_t bufsz).

  Without X-Forwarded-For:
  - Upstream servers see all requests as originating from 127.0.0.1 (or the
    proxy's loopback address), losing client IP visibility.
  - Standard reverse-proxy behaviour expected by upstream frameworks (Express,
    Django, etc.) is absent.

  Without Via:
  - Proxy chain detection is impossible.
  - Hop-count loops cannot be detected.

Impact: medium — upstreams cannot distinguish client IPs; standard proxy
  headers absent; violates RFC 7239 (Forwarded) convention
Fix:
  Add client_ip parameter to build_forward_request:
    static int build_forward_request(const http_request_t *req,
                                     const char *client_ip,
                                     char *buf, size_t bufsz);
  Then after writing Connection: close, inject:
    n += snprintf(buf+n, bufsz-n, "X-Forwarded-For: %s\r\n", client_ip ? client_ip : "unknown");
    n += snprintf(buf+n, bufsz-n, "Via: 1.1 routa\r\n");
  Update both call sites (lb_forward:432, lb_begin_forward:643) to pass
  client_ip. Also consider appending to an existing X-Forwarded-For header
  rather than overwriting it for multi-hop proxy chains.
Files: src/lb/lb.c

## Issue: file_cache and graceful shutdown not initialised in example servers
Status: confirmed
Root cause:
  server_run() (server.c:199-213) calls file_cache_init() and
  routa_metrics_init() before starting the event loop. server_free() calls
  file_cache_free(). This setup/teardown is missing from examples that use
  event_loop_run() directly:

    h2_test_server.c  — no file_cache_init; calls routa_metrics_init() ✓
    h2c_test_server.c — no file_cache_init; calls routa_metrics_init() ✓
    ws_echo_server.c  — no file_cache_init; no routa_metrics_init; no
                        graceful shutdown (uses event_loop_stop on SIGINT
                        instead of event_loop_drain_start)

  Static file serving routes added via server_static() rely on file_cache_init
  having been called (file_cache.c uses thread-local storage that must be
  initialised per-thread). If static routes are added to a loop that skips
  file_cache_init, the file cache thread-local is uninitialised: reads return
  stale or garbage pointers, stat() is called on every request defeating the
  cache purpose, or a NULL-dereference occurs in file_cache_lookup.

  The examples themselves don't serve static files, so this is latent for
  those examples. But developers copying the event_loop_run pattern into
  production code that adds static routes will hit this.

  Graceful shutdown: ws_echo_server.c uses event_loop_stop() (immediate stop)
  on SIGINT rather than event_loop_drain_start() (drains in-flight requests).
  This is different from the server_run() model and can cut off active
  WebSocket sessions abruptly.

Impact: medium — latent bug for static file serving; graceful shutdown gap
  in ws_echo_server; developers misled by example patterns
Fix:
  - Add file_cache_init() + file_cache_free() calls to each example that uses
    event_loop_run() directly (or document that file_cache requires server_run).
  - event_loop_run() should optionally call file_cache_init() internally, or
    expose event_loop_enable_file_cache() for callers.
  - ws_echo_server.c: replace event_loop_stop() with event_loop_drain_start()
    in the SIGINT handler for graceful WebSocket teardown.
Files: examples/h2_test_server.c, examples/h2c_test_server.c,
       examples/ws_echo_server.c, src/core/event_loop.c
